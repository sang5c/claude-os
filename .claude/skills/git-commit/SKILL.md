# git-commit

변경사항을 읽고, "왜" 바꿨는지에 초점을 둔 한글 커밋 메시지를 만들어 커밋까지 수행한다.

## Workflow

아래 순서를 그대로 따른다.

1. **현재 상태 파악** — 다음을 병렬로 실행한다.
   - `git status` (untracked 포함, `-uall`은 사용 금지)
   - `git diff` (staged + unstaged 모두)
   - `git log --oneline -10` (이 저장소의 메시지 스타일 참고)

2. **변경 분석 + 메시지 작성**
   - 변경의 성격을 파악한다: 새 기능 / 기존 기능 개선 / 버그 수정 / 리팩터링 / 문서 / 테스트 등.
   - **자유 형식 한글 한 줄**로 작성하되, *무엇을* 보다 *왜* 바꿨는지에 초점을 둔다.
   - 변경이 여러 갈래면 한 줄 요약 + 빈 줄 + 본문 불릿으로 세부를 적는다.
   - 동사로 시작하고 간결하게 ("추가", "수정", "정리" 등).

3. **사용자 확인**
   - 작성한 메시지(들)와 커밋 대상 파일 목록을 사용자에게 보여준다.
   - secret 의심 파일(`.env`, `credentials.json`, `*.key` 등)이 있으면 staging 전에 경고한다.

4. **staging + 커밋**
   - `git add`로 **파일명을 명시**해 추가한다. `git add -A`/`git add .`는 의도치 않은 파일 포함 위험이 있어 피한다.
   - HEREDOC으로 메시지를 전달해 커밋한다 (아래 예시 참고).
   - 사용자가 명시적으로 요청하지 않으면 `--amend`, `--no-verify`, force push는 하지 않는다.

5. **검증** — 커밋 후 `git status`로 성공을 확인한다. pre-commit hook이 실패하면 원인을 고치고 **새 커밋**을 만든다 (실패한 커밋을 amend 하지 않는다).

## 커밋 명령 예시

```bash
git commit -m "$(cat <<'EOF'
캐시 키에 카테고리 파라미터 누락되어 다른 조건 결과가 재사용되던 문제 수정

- @Cacheable key에 categoryId 추가
- 관련 테스트 보강
EOF
)"
```

## 주의

- 사용자가 명시적으로 요청하지 않으면 자동으로 커밋하지 않는다. 항상 확인을 받는다.
- 변경이 없으면 빈 커밋을 만들지 않고 그 사실을 알린다.
